Coordinates whose `units` attribute looks like `"<unit> since <reference>"`
(e.g. `"days since 2000-01-01"`) are recognised as **time axes** and decoded at
open, following a **primitives-plus-sidecar** model:

- `coord.values` stays **primitive**. For **standard / proleptic-Gregorian**
  calendars it holds **epoch milliseconds** (not the raw `days since …` numbers),
  and `coord.dates()` gives you a `Date[]`. For other calendars it holds the raw
  encoded numbers and `coord.decoded === false`, so you never get silently-wrong
  `Date`s.
- Every recognised CF calendar — including non-standard ones like `noleap` and
  `360_day` that JS `Date` cannot represent — is additionally decoded into
  calendar-aware [`cftime-ts`](https://github.com/charles-turner-1/cftime-ts)
  datetimes, available as the sidecar `coord.cftimes()`. `coord.calendar` names
  the resolved calendar.

:::danger[`coord.values` means different things on different calendars]
`values` is **not** a uniform "decoded time" the way it is in Python xarray.
Its meaning **depends on the calendar**:

- **standard / gregorian / proleptic_gregorian** → **epoch milliseconds**
  (unit-normalised; `dates()` gives `Date[]`).
- **any other calendar** (`360_day`, `noleap`, `julian`, …) → the **raw encoded
  numbers straight from the file** (e.g. `[0, 30, 60, 90]`), and
  `decoded === false`.

If you grab `.values` to build a time axis and feed it a `360_day` coordinate,
you get raw offsets, **not** timestamps — and nothing throws. The axis is just
silently wrong.

**`cftimes()` is the one accessor that is correct for every calendar** (it is
populated for standard calendars too). Reach for `cftimes()` — not `values` —
whenever you want the actual dates and can't guarantee a standard calendar.
Branch on `coord.decoded` / `coord.calendar` if you must touch `values`
directly.
:::

## Decoding a time axis

The demo store's `time` coordinate is `"days since 2000-01-01"`.

<RunnableCell
  title="time.dates()"
  code={`const ds = await openDataset(await makeDemoStore());

const time = ds.coords.time;
console.log("isTime:", time.isTime);
console.log("decoded:", time.decoded);
// Decoded time values are epoch milliseconds:
console.log("values (epoch ms):", Array.from(time.values));
console.log("as Dates:", time.dates());`}
/>

`dates()` returns `undefined` when a coordinate is not a decodable time axis, so
it is safe to call on any coordinate:

<RunnableCell
  title="dates() on a non-time coordinate"
  code={`const ds = await openDataset(await makeDemoStore());

console.log("x is time:", ds.coords.x.isTime); // false
console.log("x.dates():", ds.coords.x.dates()); // undefined`}
/>

## Non-standard calendars

For a calendar JS `Date` cannot represent (e.g. `360_day`, where every month has
30 days), `dates()` is `undefined` and `values` are the raw encoded numbers — but
`cftimes()` still gives you calendar-aware datetimes, and you can select with a
`CFDatetime` or an ISO string:

```ts
import { openDataset, CFDatetime } from "xarray-ts";

const ds = await openDataset(store); // a 360_day "days since 2000-01-01" axis

const time = ds.coords.time;
time.decoded; // false — no JS Date for 360_day
time.calendar; // "360_day"
time.cftimes()?.map((d) => d?.isoformat()); // ["2000-01-01...", "2000-02-01...", ...]

// Select by a calendar-aware datetime or an ISO string:
const label = new CFDatetime(2000, 3, 1, 0, 0, 0, 0, { calendar: "360_day" });
await ds.get("tas").sel({ time: label }).values();
await ds.get("tas").sel({ time: "2000-02-01" }).values();
```
